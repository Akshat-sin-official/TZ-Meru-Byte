# 01 — Product Requirements Document (PRD)

## 1. Product definition
**Product:** Campora (working name)

**Product goal:** provide CIT with one reliable system to generate and operate its teaching timetable, schedule midsem exams, allocate Spectra venues, process schedule disruptions, and explain/approve operational changes without creating hard-constraint clashes.

**Primary product principle:** a deterministic constraint/decision engine is the authority for scheduling and booking validity. Natural-language AI is an interface layer, never the authority.

## 2. Client and operating context
CIT has approximately 1,000 students across three years and five branches. Timetables are currently spreadsheet-based; room bookings are handled through calls and messaging. Week 7 is a high-conflict period because regular teaching continues while Spectra needs specialist venues.

## 3. Users and outcomes
| Role | Primary outcome |
|---|---|
| Admin / Dean's office | Generate schedules, administer data, resolve/approve changes, approve bookings that displace classes, configure priority order, reset demo data |
| Department coordinator | View/manage own department schedules, request changes, book department events, approve department lab bookings within policy |
| Faculty | View own timetable, declare unavailability, request extra/moved sessions, use natural-language assistant |
| Club representative | Submit/cancel venue requests and track status/reasons |

Students do not have accounts in the proposed product. Student-group schedule changes should be visible on group timetable pages; coordinators are notified.

## 4. Product scope — mandatory capabilities
1. Generate weekly timetable for every lecture/tutorial/lab session, each exactly once.
2. Schedule all midsem exams for the exam week.
3. Convert English/Hinglish venue requests into editable structured bookings; require user confirmation before submission.
4. Decide each Spectra request: approve, reject, or offer alternative, following priority and providing a reason.
5. Process disruptions (faculty leave, room closure, new session) and propose a valid timetable with minimum movement; show exact diff; Admin approval required before application; explain infeasibility.
6. Show timetables by student group, faculty and room; pending approvals, conflicts and room utilisation.
7. Faculty AI assistant accepts schedule-change requests and returns validated alternatives or reasons for unavailability.
8. Explain decisions, including why a session occupies a slot and why a booking was rejected.
9. Admin imports starter-pack-compatible dataset/change files and exports schedule, exams and booking decisions as `schedule.json`.
10. Authorized manual scheduling; all manual placements obey hard constraints.

## 5. Recommended additions (not organiser-mandated unless separately stated)
- Drag-and-drop or tap-to-move with live validation and reason codes.
- Conditional booking options (e.g. preferred venue/time, then fallback) evaluated in order by deterministic code.
- Explicit LLM outage banner and manual fallback.
- In-app notifications generated after a change/decision is committed.
- Version history, rollback, audit trail, schedule comparison and soft-penalty breakdown.
- Background job status for solver runs.

## 6. Out of scope for hackathon unless time remains
- Student login and personalized student portal.
- Email/SMS/push delivery; in-app notifications are sufficient.
- Multi-campus / multi-institute tenancy.
- Billing, payments, attendance tracking, LMS, course registration.
- Autonomous AI approval or autonomous application of schedule changes.

## 7. Success measures / judging alignment
| Measure | Target |
|---|---|
| Base timetable hard violations | 0 |
| Required sessions scheduled | 189/189 for public dataset; dynamically match imported dataset |
| Exams scheduled | All dataset exams; 41 in public dataset |
| Approved booking hard violations | 0 |
| Disruption result hard violations | 0 |
| Reschedule movement | Minimize moved sessions; report moved count and diff |
| Manual/AI actions | Server revalidation on every write |
| Demo roles | Four usable accounts |
| Submission exports | Both generated by app and independently validator-checked |
| Availability | Manual booking and deterministic operations work when LLM is unavailable |

## 8. Product principles
- Correctness before optimization; optimization before convenience.
- Server is source of truth; client validation is advisory.
- Fail closed: uncertain or invalid proposals are not applied.
- Preserve original source data and raw user text.
- Decisions must be explainable with machine-generated reason codes.
- No manual edits to generated export files.
